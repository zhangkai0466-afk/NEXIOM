# 本地核心流式处理与超时修复

## 问题和证据

发送消息或开始研读时，核心为每个文字增量提交 SQLite 事务并同步导出完整项目历史；已有通知又连续通过微任务消费，导致 IPC、取消和定时器长时间得不到调度。界面的 30 秒请求超时并不取消已经开始的 Agent 任务。一次真实任务在原生引擎完成后约 140 秒才被 NEXIOM 记为完成；该任务模型请求返回 HTTP 200。

无网络隔离复现中，6,000 次累计文字更新导致任务耗时约 108 秒，项目导出占约 91.5 秒，状态查询最长等待约 108 秒。查询本身只需约 1–10 毫秒。旧刷新失败还可能覆盖新状态，恢复后旧错误横幅不会清除。

核查日期：2026-09-21。研究固定版本、实际源码和官方文档，没有运行第三方 Agent，也没有复制其配置、提示词或认证信息。

Claude Code CLI 的完整内核并非该 MIT SDK 的公开源码，不能称这里审阅了它的全部内核。Hermes 的33ms机制会逐条发送合并调度的帧，并非只发一个拼接帧。OpenCode 的8ms策略来自前端消费循环，不能据此推断其所有后端都这样做。上述50ms/1s等 NEXIOM 参数是本项目取舍，并非照抄这些项目的默认值。

详细源码证据在 `output/timeout-research/claude/evidence.md`、`hermes/REPORT.md`、`opencode/EVIDENCE.md`，包含固定提交链接和未采用的机制。

## NEXIOM 的处理边界

1. 通用 Agent 协调层合并相邻、同一 item 的累计文字/命令输出快照，约50ms提交最新状态。累计全文采用替换而非拼接，避免重复正文。跨 item、工具、错误、上下文和结束事件保序；源静默也能保存已收到的 partial。
2. 原生通知层和通用事件消费层都有次数/时间预算，并通过 `setImmediate` 真正让出事件循环。原生层包含不产生可见输出的通知，避免过滤路径再次饿死 IPC。保留原有队列上限、会话隔离和30秒请求超时。
3. SQLite 仍是本机状态来源。流式期间的 `.nexiom/project.json` 是便携镜像，使用不因新输出而重置的1秒定时器；普通命令、最终完成/失败/取消和退出时立即导出。仍采用原有临时文件加原子替换方式，写入失败保留 dirty 状态并报告。
4. 界面状态刷新采用统一调度和可恢复错误状态，禁止旧请求失败覆盖新成功。刷新成功只清除刷新错误，不抹掉发送/文件操作等独立错误。只重试只读状态刷新，不重发 Agent 任务。

异常退出仍可能丢失最后一个尚未提交的短窗口内的文字；项目便携镜像正常运行时可比数据库落后约1秒。正常完成、取消和关闭会补齐保存。该设计不改变 SQLite 的 WAL 或 durability 设置。

## 验证要求

- 复用原6k/12k隔离负载，比较总耗时、导出次数和 IPC 排队时间；结果不能只看最终文本。
- 检查流式累计文本无重复、跨 item 保序、工具结果与上下文不丢、已结束 item 不被晚到更新重新打开。
- 检查源静默时 partial checkpoint、异常/取消时保存、正常关闭与重启恢复。
- 检查无可见输出的原生通知洪流仍允许计时器/取消运行。
- 检查刷新失败的自动恢复、旧请求竞态、独立错误保留和卸载清理。

合成测试不调用付费模型，不会修改用户正在使用的工作区。性能结果说明所复现瓶颈的改善，不代表任意磁盘故障或任意模型网络问题都已消除。
