# NEXIOM 建模伙伴功能设计草案

日期：2026-09-19。状态：领域功能提案，尚未整体确认或实现；导航、按问题组织对话和本地账户已获授权，进入 0.4.0 接入。

用户已明确：当前 NEXIOM 尚不能承担完整实际建模工作，需要继续设计功能、逐步实现和验证。本稿将 [国赛复盘](21-competition-retrospective-and-partner-principles.md) 转化为具体产品行为。最新授权先将已确认的导航与账户功能接入真实应用，不表示本稿九项能力已整体完成。

## 1. 产品要达到的工作状态

用户打开一个项目，NEXIOM 能说明当前研究什么、有哪些可靠结果、还缺什么、建议下一步做什么及其理由。用户可以讨论、纠正或交给它继续执行；换一个会话或交给队友后，已有决定、结果与未决事项仍能被正确理解。

用户希望伙伴理解自己的要求和决策依据，并能吸收经验。功能上需要把这种理解落到可查看、可修订的偏好、实例、项目决定和工作流程中。长期目标一致，同时保留针对具体判断提出异议的能力。

以下能力围绕同一个项目协作。界面入口的数量、模型数量和 Agent 数量不能直接由能力数量推导。用户已确定左侧先添加和列出赛题项目（对应解题工作区文件夹），点击项目后以动画进入该项目的八维导航：项目总览、赛题研读、附件分析、开始建模、模型检验、图表设计、论文写作、检查交付。具体见 [工作区导航设计](23-modeling-workspace-navigation.md)。不同项目的状态保持独立，项目内各维度共享本题依据。

开始建模、模型检验、图表设计、论文写作四项可展开并添加针对具体问题的对话，列表菜单支持重命名；开始建模使用用户实际提供的“二级图标.svg”。添加对话弹窗仅保留“问题”和“对话名称”字段，名称可选并默认采用问题名。界面删除所有说明性小字，保留必要标签、操作名称和错误反馈。

对话以项目、问题、工作维度和对话四类标识关联，同一问题跨维度使用相同问题 ID。本轮接入真实项目、问题与会话的持久化，旧会话保留原有身份和历史并归入“开始建模”。每个对话的记录与草稿独立；后续需要让相关对话引用同项目已采用的条件、成果和依赖，不能把全部对话全文串接代替语义关联。问题 ID 的建立不等于成果传播与依赖复核已经实现。

用户明确拒绝上一版导航点击后的内容界面。2026-09-20 用户进一步明确：赛题研读入口只选择赛题文件，不提供正文输入或复制粘贴；点击已选 PDF 时在右侧展开查看器，确认后自主分析。原题研读、逐问研读、陷阱与歧义等成果按规范化板块呈现；人工纠偏绑定当前板块，独立保存记录与草稿，栏宽可调且不覆盖正文。PDF 原题可嵌入工作台查看，当前先实现文件级文字批注，页码坐标和划词高亮留待专用批注数据模型。附件分析同样使用“输入附件—固定 workflow 分析—按附件形成报告—人工纠偏”的专用工作台；每个附件的报告、纠偏历史和编辑草稿相互隔离，纠偏运行只替换目标附件的最新报告。检查交付仍进入本项目内的单一持久化对话。项目总览不使用聊天框，后续承载总调度、成果查看和论文 PDF 成品查看界面。图表设计已接入的资源库与工具继续保留，见 [图表设计与资源库](25-visual-design-integration.md)。导航名称不等同于功能归属：已有编程执行能力也需要进一步组织为可追溯的建模实验与求解流程。用户可以从审题、已有代码、半篇论文或一次结果复核中的任何位置开始，不要求线性完成八个入口。

两层侧栏底部只保留账户栏目，支持头像和昵称，点击后从菜单进入设置；暂不增加“协作经验”“项目文件”。账户页保存本地资料，以蓝色小方块按日期呈现 NEXIOM 已记录的 token 用量，颜色越深表示用量越多。这是本机运行记录的展示，不代表新的云端登录或供应商账户额度；统计与缺失值边界见 [工作区导航设计](23-modeling-workspace-navigation.md#6-本地账户与-token-用量)。

## 3. 关键交互与功能约束

### F-01：如何逐渐理解用户

用户可以直接说“这个方案太复杂”“这段话不符合我的表达”“这条经验以后要记住”，也可以给出满意与不满意的实例。Agent 应识别反馈对象，说明会如何修改当前工作；需要形成长期经验时，保存原反馈、归纳规则、适用范围和例外。

- 明确要求长期记住的偏好可直接记录并告知；由模型推测的偏好先作为候选，不悄悄变成长期指令。
- 单题假设默认留在本项目；“这次采用定义 A”不能成为所有项目的固定定义。
- 用户可以查看、更正、禁用和删除经验。更正已用于当前工作的规则时，需要检查相关成果，而不只是改一条记忆。
- 多条经验冲突时，根据当前要求、来源和适用范围说明选择；影响很大的冲突集中询问，普通措辞偏好可先作可逆调整。
- 长期经验采用摘要与相关内容检索，保留原始出处；不能把全部会话无限追加到每次请求。

后续验收场景：用户将图表偏好从高饱和配色改为适合黑白打印，下一次绘图采用新要求；旧方案保留历史记录；无关项目的数学假设不随之改变。这里改善的是记忆和工作方式，不默认涉及模型参数训练。

### F-02、F-04：遇到定义歧义时如何讨论

用户导入材料后，Agent 先给出它对题目与数据的理解，并允许直接在原文旁纠正。文档中的公式、图片和表格解析不可靠时应定位具体位置，缺失信息保持缺失，不能生成一个看似完整的题意。

遇到会影响后续计算的定义冲突，呈现少量真正不同的解释，分别说明依据、适用条件、量纲、计算区别和受影响问题。检索需要保存实际读到的来源位置和相关内容；搜索摘要不能自动当作完整依据。

讨论结果应进入当前项目决定，并关联方案与任务。决定尚未解决时，标记依赖它的工作；与其无关的读取、数据检查和文稿结构整理仍可继续。对可逆且影响有限的选择，声明暂定处理并推进，避免把每个细节都交回用户。

后续验收场景：两种定义都可能成立时，Agent 能说明为什么选择其一、哪些结果依赖此选择；后续用户改变定义时能找到影响范围。场景仅用于设计，不裁定本次国赛的定义。

### F-03：整题关系如何持续有效

每一问保存要求、输入、输出、假设、约束、变量和来源；小问之间的关系应有明确理由。前问的条件逐项区分继承、修改、不适用或待核实。界面可以先呈现简表，关系复杂时再展开图，不能用一张固定流程图强行解释所有赛题。

修改会产生新版本。项目应计算已经登记的依赖，并由 Agent 补查可能遗漏的语义关联。受影响的实验、图表与正文标记为待更新或待复核，旧版本仍可查看；未经重算不得自动把旧数值换上新标签。

后续验收场景：用户更改第二问的一个约束，系统定位引用该约束的模型、结果与段落，并说明哪些后续问题需要复查。不存在依赖的问题继续保持有效；无法确定的关联明确显示待核实。

### F-05、F-08：如何区分算完、检查通过与结论可用

每次实验记录真实使用的数据、代码、环境、参数、评价办法、结果与日志。程序执行成功只表示本次运行结束；数值检查、模型假设是否适用、论文能否据此下结论分别表达。

预测任务需要记录决策时刻与输入可用性。验证划分要适应时间、样本实体和分组结构；预处理和调参不能越过对应训练数据边界。优化任务要检查可行性、约束残差及实际获得的求解状态。仅有可行解时不能标作已证明全局最优。优化决策只使用该时刻实际可获得的已知量或预测值；事后真实值用于评价，若用于理想信息上界对照应单独标注，不能混为可实施策略。

Agent 负责提出检查和解释；能确定执行的单位、版本、数值与约束检查交给程序。语义判断保留证据和不确定性，不给出一个笼统的“无泄漏”或“完全正确”标志。复核视角可以由当前 Agent 切换承担，独立模型复核作为可扩展能力，不以模型投票代替证据。

失败实验应能定位原因、保留日志并从明确的步骤继续。重试有约定范围和预算；工具失败、环境缺失、结果不满足要求采取不同处理，不能依靠重复发出相同请求无限循环。

### F-06：论文如何成为工作过程的一部分

从题意与初步方案形成时建立论文结构和符号表；逐步补入已明确的方法、已验证结果及解释。未完成计算保留显式空缺。论文段落可以向 Agent 提问“这一步为什么成立”，并回到对应推导或实验。

用户可以修改正文、要求改写局部、保留自己的表达。更新方法或结果时，先关联到具体段落并展示修改；检测外部编辑，不能整章重新生成后覆盖用户成果。模型变了但结论未重算时，论文显示依赖待复核。

符号应保存含义、单位和使用范围，发现同符异义、公式编号与引用错误。引用管理保留真实来源；有出处不代表出处支持当前结论。导出应检查中文、公式、表格、图注和分页，保留可编辑源文件。

DOCX 是否为首版主要编辑和交付格式，以及 Markdown/LaTeX 与外部编辑器如何往返，仍需后续细化；当前草案不把既有格式建议视为已确认决定。

### F-07：可视化设计 MCP 放在哪里

可视化能力接收数据或结果版本、表达目标、图型约束、目标版面和风格参考，输出图、源文件、图注与数据关联。用户可以说“突出两种策略的差异”“保留信息但减少拥挤”，Agent 应将要求落实到图表修改并解释必要取舍。

现有可视化 MCP 可作为这项能力的一种执行工具。当前应设计接入协议、编辑往返、版本保存和失败恢复；具体适配需要读取其实际接口后才能确定，不假定它已经支持这些能力。

统计聚合、平滑、删点或尺度改变可能影响含义，需要作为明确的数据变换或表达选择记录。工具不可用时应支持基础绘图；论文引用关联到已选图版本，不能让预览改了而导出的仍是旧图。

### F-09：如何让用户掌握全局并分担工作

项目概览显示各问与论文的实际状态、当前任务、待决问题、主要缺口和负责人。进度由有证据的完成条件说明，不用任意百分比伪装研究进展。

队友可负责完整模块。Agent 根据已有工作生成任务说明和交接材料，导入队友的代码、文稿或结果后进行版本与一致性检查；首版可以通过文件交接完成，不依赖多人实时同步。对外发送材料由用户明确授权或自行完成。

截止时间用于规划与提醒，实验限制用于控制具体运行，二者分开。用户可说明当前优先提高质量、补齐覆盖或完成交付，Agent 据此调整任务顺序并说明代价。最终导出固定论文、图表、代码和复现说明的版本，区分“已生成”“检查通过”和“已提交”。

## 4. 自主程度与用户控制

具体权限沿用已有执行边界；以下描述未来协作体验，不增加每一步的确认弹窗。

| 情形 | 建议行为 |
| --- | --- |
| 当前目标和范围内的阅读、实现、调试、实验、作图、整理 | 持续推进，汇报有意义的发现与产物；继承仍有效的授权 |
| 可逆、影响有限的方法或呈现选择 | 说明采用理由，记录必要假设，允许用户纠正 |
| 改变核心解释、研究目标或超出已约定预算 | 展示具体选项、影响和建议，只集中询问真正缺失的决定 |
| 用户中途修正目标或条件 | 明确已收到、正在更新还是尚未生效；更新计划与影响范围；无关工作继续 |
| 结果完成但仍有检查缺口 | 清楚给出可用结果与缺口，不能通过完成工具调用冒充研究完成 |

用户不应先填完术语表、任务表和实验表才得到帮助。Agent 从材料、对话和工具结果维护结构化状态；需要用户判断的内容以简短、可核查的方式呈现。

用户已经用自然语言明确决定且对象、范围无歧义时，应绑定到具体方案版本并继续，不要求在聊天、计划和弹窗中重复批准同一件事。内部区分执行授权、检查结果与用户接受，不意味着每个阶段都等待用户签字；对计算结果的程序检查应自主完成。

## 5. 一个贯通功能的设计场景

以下是拟实现的交互，不表示当前应用能够完成：

1. 用户导入赛题和数据。NEXIOM 解释各问要求、数据含义和暂不确定的条件，并提供原文跳转。
2. 发现关键定义有歧义，Agent 给出依据与影响。讨论形成采用理由后，保存本项目决定，更新相关方案。
3. 用户确定研究方向，Agent 在范围内计算并验证基线；形成结果后同步补入相应文稿，保留缺口。
4. 用户要求修改一个假设。NEXIOM 显示相关问题、实验、图表和正文，按新版本重算并复核，不覆盖历史或遗漏用户编辑。
5. 用户将一问交给队友。NEXIOM 整理输入、假设、产物要求和当前状态；接收成果后核对与整题是否一致。
6. 用户要求完善某张图并准备论文。可视化工具修改选定图，文稿引用更新到相应版本；导出前提供具体缺失项与检查结果。

这个场景的关键是同一项决定能贯穿计算、图表和写作。各模块分别能生成内容，还不足以实现这一体验。

## 6. 功能如何落到已有架构

沿用现有项目、任务、实验、证据与论文的设计边界，补充功能需要的信息。本轮导航接入会保存问题与维度关联；下表其余内容仍是待细化的归属，不表示整套领域结构已实现。

| 需要保存的内容 | 现有设计承接处 | 需要补充的契约 |
| --- | --- | --- |
| 用户偏好与经验 | 项目记忆、上下文选择 | 个人与项目范围、来源实例、候选/采用/停用状态、版本与撤销 |
| 按问题关联的对话 | 项目、会话、上下文选择 | 本轮接入项目/问题/维度/对话身份与跨维度问题 ID；后续补足共享依据的来源、范围与成果引用 |
| 术语、假设与决定 | ProblemSpec、ModelSpec、Source、Claim | 候选解释、选择理由、条件继承、复议条件 |
| 各问和成果的联系 | Task、资源版本、EvidenceLink | 带依据的跨问依赖、受影响对象、待更新/待复核状态 |
| 方案与信息边界 | PlanRevision、EvaluationProtocol | 决策时刻、变量可用性、比较成本、停止条件 |
| 文稿与可视化设计 | PaperBlock、Artifact、ResourceVersion | 符号范围、用户修改、图表意图、风格、生成源文件与导出绑定 |
| 检查与交接 | ValidationCheck、Task、ExportManifest | 检查覆盖范围、负责人、交接包、接收后的冲突处理 |

在接口明确前，不为每项能力单独增加服务或 Agent。不用一套固定提示词替代需要持久化、校验和事件驱动的功能。

## 7. 接下来如何继续设计

建议按依赖分三轮细化，当前首先推进第一轮；九项能力保留在整体蓝图中。

1. **伙伴与项目的共同工作方式。** 细化 F-01、F-03 和自主程度：它记住什么，哪些内容是当前依据，用户纠正后怎样生效，如何恢复和交接。交付具体对话场景、状态及页面草图。
2. **从题意到可靠结果。** 细化 F-02、F-04、F-05、F-08：审题与资料定位、方案讨论、环境和实验、结果检查、异常恢复，并明确与第一轮状态的联系。
3. **从研究过程到论文交付。** 细化 F-06、F-07、F-09：持续写作、图表设计、外部文件往返、团队分工、进度与导出。

每项设计说明至少覆盖：使用场景、输入、触发条件、Agent 动作、用户可见反馈、持久状态、纠正与异常路径、功能依赖、未来验收场景。验收场景可以现在设计，实际验证随实现逐步开展。

后续需要讨论的取舍包括：跨项目个人经验与项目记忆的界面；用户希望亲自决定的范围；论文编辑和导出格式；可视化 MCP 的实际接口；子 Agent 最先承担哪类独立任务。这些待决项不阻止其余功能设计，也不默认用户已接受本稿的具体方案。

当前阶段完成的依据是功能之间能连贯工作、关键行为与异常路径足够明确，能够指导后续实现。产品可用性要由实际实现和验证另行证明。
