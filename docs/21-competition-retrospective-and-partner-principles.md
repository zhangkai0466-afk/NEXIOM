## 1. 用户希望保留下来的经验与目标

暑假初期，用户尝试开发多 AI 头脑风暴 MCP，希望通过多模型与多种 Agent 工具获得更好的建模方案。请求编排、上下文与稳定性问题消耗了大量时间和费用，最终转向人工协同多个 Agent。用户认为，同期更需要练习限时解题、论文写作与完整交付。另有一个可视化设计 MCP 半成品，用户认为具备一定价值，希望后续考虑融入 NEXIOM；本次尚未检查其实现与效果。

据用户回忆，本次选择 C 题后：

- 第一问的“充放电效率”存在不同来源的定义差异，团队花费较多时间判断，最终采用主流文献中的用法。
- 第二问需要处理预测与优化的关系，并避免数据泄漏，投入了较多时间与模型调用。
- 第三问是否沿用第二问的条件或假设存在疑问，形成较满意结果时已经到周六晚上。
- 第四问在疲劳状态下被相对独立地处理，用户事后认为其结果与前三问衔接不足。
- 主要依靠 AI 生成的首版论文在周日早上才形成，后续修改正文、符号和图表的时间不足，直到截止前十几分钟才提交。
- 用户承担了主要建模、写作与判断，队友主要参与作图，任务分配没有充分分担核心工作。

用户希望打造理解其目标、要求与决策依据的建模伙伴，能吸收经验并持续磨合，辅助完成整个建模过程，以国一为努力目标。用户也计划系统学习建模、可视化与写作，以增强自己的判断和比赛掌控能力。

这里需要修正的是投入顺序和验证方式：多方讨论可能有价值，但尚未证明能改善比赛表现的工具研发，不宜长期挤占实战训练。一次项目受挫不足以证明多 Agent 本身无效。

## 2. 伙伴应当理解什么，承担什么

**对齐目标、质量标准和取舍依据，同时保留提出异议的能力。** 当用户判断缺少证据、某个结论与前文冲突、或方案会显著挤压交付时间时，Agent 应明确指出依据、影响及可行替代。用户保留关键取舍权；已确定范围内的检索、实现、实验和整理应持续推进。

理解用户需要逐步积累具体信息，例如：什么证据足以采用一种定义；效果改善多少才值得增加复杂度；哪些表达与图表清晰可用；何时应停止试验并完成论文。这些标准不能仅靠“追求最好”推断。

保存经验、修改流程和用案例检验表现，属于系统与协作方式的改进，不等于在对话中改变底层模型参数。更强的模型也不能保证每次判断正确；国一是长期目标，不能作为产品能够保证的结果。

建议将经验分开保存，并为每条记录保留来源、适用范围、状态和修订日期：

| 内容 | 示例 | 使用方式 |
| --- | --- | --- |
| 稳定偏好 | 重视推导可解释、数值可复现、图表表达准确 | 跨任务参考；用户的新要求可以修订 |
| 当前项目决定 | 某术语的定义、某问采用的假设和单位 | 限定到该项目、问题和版本，不迁移成普遍事实 |
| 候选经验 | 本次因成稿过晚而压缩了检查时间，建议更早维持完整草稿 | 在之后训练中验证、修订或撤销 |
| 已验证流程 | 某种检查在多个案例中发现了具体泄漏或矛盾 | 记录案例与局限，作为后续可复用流程 |

近期可以用简短文件实现这些记录。当前 `.nexiom/MEMORY.md` 由用户维护，每次任务加载；它尚不具备自动提取、来源检索和经验有效性评估。长篇复盘保留在文档中，工作记忆只放本轮相关的简短规则与来源，避免不断注入全部历史。

## 3. 从这次经历得到的六项协作机制

### 3.1 术语冲突与条件歧义：形成可复查的决定

触发条件：关键术语存在多种定义，或者原题对条件继承、评价范围等表述不明确。

Agent 应给出原题位置、候选解释、各自来源及适用条件、单位与计算差异，以及对后续模型的影响。题目明确给出的定义优先；题目未明确时，应结合语境与来源的适用范围判断，不能简单以“国标”或“文献多数”为唯一依据。仍有歧义时，明确声明采用的解释，并在费用可控的情况下比较另一解释是否改变主要结论。

只有会实质改变目标、可行域或大范围返工的未决取舍需要集中交给用户。可逆的小选择可以声明暂定解释、记录复议条件并继续推进；独立工作不必一起停下。避免对每种解释无限分叉。

验收：新会话或队友能够从记录说明“采用了什么、为什么、影响哪些问、何时需要重议”。不能只记录一个最终答案。

### 3.2 预测与优化：按决策时刻检查信息

触发条件：任务使用预测值支持后续决策，或按时间产生观测数据。

在选择复杂模型前，写清预测目标、预测时刻、预测跨度，以及每项输入在该时刻是否可获得。根据数据生成方式与实际决策场景选择验证划分；存在时间依赖时采用时间划分或滚动验证，同时检查样本实体、分组等其他泄漏来源。预处理参数、特征选择与模型调参必须遵守各训练折的信息边界，最终测试数据不参与选择。

优化模型应使用当时可获得的预测或已知量。事后真实值可以用于评价；若用于理想信息上界对照，必须明确标注，不能将其效果混为可实施策略的效果。同时检查预测误差对决策可行性和目标值的影响。

验收：能够指出每个输入的可用时点，复现评价协议，并证明报告中的可实施策略没有使用未来真实信息。代码能运行或指标很高，都不足以通过此项检查。

### 3.3 分问衔接：保存输入、输出与假设的关系

触发条件：开始新小问，或修改上游定义、假设、数据与模型。

每问维护一张简表：题目要求、输入来源、输出、单位与符号、假设、约束、依赖的问题、对后续的影响。对前问条件逐项标记“继承、修改、不适用、待核实”，说明依据。不能默认所有条件沿用，也不能默认每问独立。

上游改变后，列出需要重新检查的实验、数值、图表及正文；既有结果保留为旧版本，未经复核不能继续作为当前有效结论。

验收：能解释综合问与前文的方法和结果如何连接；将一个上游参数或假设改动后，能够找出受影响的产物。具体依赖边必须由原题与模型确定，本文不预设本次第四问的正确结构。

### 3.4 解题与成稿并行：持续保有可阅读的版本

触发条件：完成初步审题后即开始，不等待所有问题解完。

先建立论文骨架、符号表、数据说明和各问的基本求解路线；形成经验证的阶段结果后，及时补入方法、结果与解释。未解决部分显式标为待完成，不能让流畅文字掩盖缺失计算。

先争取覆盖各问且相互一致的简单方案，再比较升级方案的收益、运行费用、验证成本和写作成本。文稿中的每个关键数值应能定位实验结果，图表应能定位数据与生成脚本。

比赛计划需预留完整初稿、方案冻结、导出复核和提前提交的时间。具体节点在限时训练中校准；不得把时间安排变成执行引擎对所有任务强加的固定超时。冻结之后，优先修复会影响正确性和交付的问题，新增模型需要明确的收益依据。

验收：记录首次覆盖各问的完整草稿时间、剩余缺口和提交余量；任何时候都能说明当前已经有哪些可靠内容，哪些尚未验证。

### 3.5 分工与疲劳：让工作可以被接手和验收

触发条件：安排任务、连续工作后需要休息，或者核心工作积压在一人手中。

按完整工作模块分配责任，例如“完成某问从数据到结论的可复现实验”，或“维护各问方法、结果与正文的一致性”。每项任务明确负责人、输入、产物、验收条件与复核人；队友可以承担建模和写作的实质工作。

用户可以保留全局取舍，但不必逐项亲自重做。信任来自可检查的成果：脚本、结果表、假设说明和简短交接记录。交接至少包括已确认结论、证据位置、尚未解决的问题、下一步与当前版本。关键定义、信息边界和跨问连接应交叉复核，并提前安排休息和接力。

验收：另一名队员能够据交接记录继续任务并复现主要结果；用户休息时，已有明确边界的工作仍能推进。此机制不要求先实现多人实时协作系统。

### 3.6 可视化：用可验证的表达收益决定工具价值

触发条件：已有有效数据或结果，需要表达比较、关系、变化、误差或决策过程。

先确定图要支持的论点，再确定图型、布局与样式。优先检查坐标、单位、图例、尺度、信息密度和正文引用；精细美化的投入服从完整成稿与复核时间。

用户现有可视化 MCP 的设计应明确：输入为结果表、表达目标与版面要求；输出为生成源文件、渲染图、图注和数据来源。待相关功能具备可运行条件后，再选择一类图比较人工流程与 MCP 流程的耗时、改图次数、可读性及数值一致性。工具失败时应能用基础绘图流程完成交付。

当前可以先设计其接入位置、输入输出与失败处理，后续根据实际实现调整封装并验收。无需为了保留该工具的价值而恢复原先的大规模多模型编排。

## 4. 与 NEXIOM 当前基础衔接

依据当前 README、[项目级 Agent 定位](12-project-agent-positioning.md)、[核心数据结构](04-domain-model.md)及本次查看的记忆加载实现：NEXIOM 已有真实执行内核、持久会话和项目记忆；任务依赖、实验与证据管理、自动过期检查及完整论文导出仍需实现。本文不将已有设计当作已交付功能。

用户明确指出，当前产品连半成品都算不上，尚不能开始承担建模工作。已有工程基础不能证明产品可用。下一阶段按以下顺序推进：

1. **继续设计功能。** 明确伙伴如何理解用户、分析赛题、讨论方案、求解、写作、作图、复核与交接；定义各能力之间的联系。
2. **细化可实现的功能说明。** 每项写清触发条件、输入、Agent 行为、用户可见结果、状态保存、异常处理和后续验收场景。
3. **分阶段实现与局部验证。** 功能设计收敛后逐步开发，先验证具体模块及相邻流程，不要求用户用不完整产品开展比赛训练。
4. **具备完整工作能力后再做实战验证。** 用历史题和模拟赛检验交付质量，再据真实问题修正功能与协作机制。

当前功能设计见 [建模伙伴功能设计草案](22-modeling-partner-functional-design.md)。本文的机制、模板和后续训练建议不表示应用已经能够自动执行这些工作。

## 5. 用一年的训练积累证据

以下是后续学习与验证的参考。自主学习可以按用户自己的安排开展；使用 NEXIOM 做练习和模拟赛，以相关功能实现并通过基本检查为前提，不是当前产品设计的先决条件。

| 阶段 | 实践重点 | 留下的证据 |
| --- | --- | --- |
| 当前设计阶段 | 将本次经历转为功能需求，明确关键交互、跨问联系与异常处理；整理可用于后续验证的材料 | 功能说明、交互场景、依赖与待决事项 |
| 局部功能可用后 | 选择对应小问或片段验证审题、计算与论文衔接 | 原判断、修正依据、可运行结果与文稿差异 |
| 基础积累期 | 系统学习建模、统计验证、优化、写作和科学绘图；用小题做限时练习，每次聚焦一两项机制 | 方法笔记、结果解释、适用条件及错误案例 |
| 综合训练期 | 定期做整题模拟，三人轮换承担建模、实现、写作和复核；为开发设独立时间预算 | 完整交付时间、协作记录、费用和缺陷清单 |
| 临赛阶段 | 按真实赛事允许的工具与提交要求演练，稳定工作流、环境、模板和交接习惯 | 多次按时完成的论文与复现包，明确的备用流程 |

功能设计可以依据本次复盘、完整工作流程和已知能力缺口推进，无需先完成新的练习才有资格设计功能。进入实现和使用阶段后，再结合可复现的案例检查收益；当前不替用户设定开发或训练的时间配额。

每次训练至少记录：首次完整草稿时间、截止前剩余时间、返工原因及耗时、发现和漏掉的跨问矛盾、关键数值是否可追溯、核心计算能否重跑，以及模型调用费用。人工纠错次数可辅助观察，但次数下降也可能意味着检查不足，需要结合独立复核发现的遗漏判断。

修改工作流后，既重跑出现过问题的案例，也使用未参与规则制定的新题片段，避免只学会应付已知案例。比较时记录模型版本、时间预算与工具条件；不能因一次好结果就认定机制可靠。

## 6. 供功能设计使用的工作记录示例

以下字段用于讨论产品需要保存什么、如何支持后续交接与验证。最终由 Agent 和工具根据实际工作维护，用户应能查看和修订，不要求用户现在逐项填写：

```text
任务 / 小问：
时间和费用预算：
题目要求与原文位置：
术语、单位、候选解释及来源：
当前采用的解释、理由与复议条件：
承接的输入、假设与输出给后问的内容：
决策时刻可获得的信息 / 禁止使用的未来信息：
基线方法与验收办法：
数据、代码、环境、结果的位置与版本：
已写入论文的结论及证据：
待验证项、负责人、复核人和交接下一步：
实际耗时 / 费用 / 返工原因：
本次候选经验及下一次检验方式：
```

当前阶段的完成标准是形成连贯、可讨论、可实现的功能设计，能说明用户如何协作、Agent 如何行动、结果如何保存与检查。之后分别推进实现、局部验证与整题验证，不能把写完设计文档视为产品已经可用。
