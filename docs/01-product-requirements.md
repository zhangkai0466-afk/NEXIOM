# 产品需求总纲

状态：v0.1 评审草案。用户已确认项见 [决策索引](README.md)。

2026-09-19 补充：当前产品尚不能承担完整实际建模工作，领域能力继续设计、逐步实现和验证。用户已授权将确认的导航、按问题组织对话和本地账户接入真实应用。本需求总纲仍是目标要求，不能作为已实现能力清单；伙伴理解、经验积累、分问关联和持续写作等具体设计见 [建模伙伴功能设计草案](22-modeling-partner-functional-design.md)。

## 1. 产品定义

NEXIOM 是围绕数学建模项目持续工作的桌面 Agent：理解赛题与附件，与队员讨论并确认方案，操作项目文件和工具，执行数值实验，核对结果，协助完成有依据、可复现的论文与提交材料。

最重要的产品结果是：用户能知道一个结论来自哪个数据版本、哪段程序、哪次实验和哪组假设，并能重新运行和修改它。自然语言是入口，项目状态和实验记录才是长期工作依据。

首版用户是操作本机的队员。模型手、编程手、论文手是工作视角，不在首版映射为账号角色或必须同时存在的三个 Agent。队伍通过项目导出和已有协作工具交接，首版不承诺多人同时编辑。

## 2. 面向数学建模的交互组织

左侧采用两层导航：初始添加和列出赛题项目，每个项目对应一个解题工作区文件夹；点击项目后，通过动画进入该项目的八个工作入口：项目总览、赛题研读、附件分析、开始建模、模型检验、图表设计、论文写作、检查交付。用户已确认此方向及名称，详见 [工作区导航设计](23-modeling-workspace-navigation.md)。项目内提供“所有赛题”返回入口；添加项目后留在列表，由用户点击进入。

开始建模、模型检验、图表设计、论文写作四项可展开，各自下方添加和选择针对具体问题的对话；列表项菜单支持重命名，并保持问题关联与对话历史。“开始建模”采用用户实际提供的“二级图标.svg”。添加对话弹窗只含“问题”和“对话名称”字段，名称可选，留空时采用问题名称。所有说明性小字删除，必要的字段标签、操作名称与错误反馈保留。

项目、问题、工作维度和对话分别标识，同一问题跨四个维度共享问题 ID。本轮接入真实项目、问题和会话的持久化；已有会话保留身份和历史并归入“开始建模”。每个对话的内容与草稿独立。后续需要让同项目既定条件、成果及其依赖按相关性共享，不把全部对话全文串接为上下文；语义上下文选择、成果传播和依赖复核仍待实现。

用户已明确拒绝上一版点击入口后的内容界面。最新补充项目总览、赛题研读、附件分析、检查交付各自也应有聊天框：点击直接打开本项目该维度唯一的持久化对话，继续使用已有基础对话能力，各入口的具体领域功能待用户后续定制。不恢复旧版卡片、公共分问筛选或右侧伙伴面板。已接入的图表资源库与工具继续保留，见 [图表设计与资源库](25-visual-design-integration.md)。主对话的分析呈现与输出形式继续参考 Claude Code。各工作维度应共享同一项目的决定与成果，不同项目保持独立状态。项目没有 Git 时仍可工作；文件快照与实验版本不依赖 Git。

两层侧栏底部只保留账户栏目，显示可设置的头像和昵称；点击账户菜单进入设置。暂不加入“协作经验”“项目文件”入口。设置中的账户页保存本地个人资料，并以按日期排列的蓝色小方块展示 token 用量，颜色越深表示当天已记录用量越多。用量来自本机 NEXIOM 的实际运行记录，未知用量不伪装为零，也不冒充供应商账户全量消费、剩余额度或账单；本地资料不等于新增云端登录。

| 能力 | 目标行为（具体页面待设计） |
| --- | --- |
| 赛题项目与建模导航 | 添加工作区文件夹为赛题项目；点击项目以动画进入八维导航；可返回项目列表；不要求按顺序通关 |
| 项目与会话 | 四个工作维度下可添加、选择、折叠和重命名对话；其余四个入口各打开独立的项目级聊天框；按问题关联跨维度工作，对话内容独立；项目状态独立保存和恢复，项目归档方式待设计 |
| 本地账户与用量 | 底部账户菜单进入设置；保存头像和昵称；按日用蓝色方块呈现真实已记录 token 用量 |
| 对话与计划 | 附加文件；讨论方案；展示待确认计划；执行中补充指令 |
| 执行记录 | 显示工具名称、目标、状态、耗时、输出摘要和错误；展开查看日志 |
| 文件与变更 | 查看文件树、文本与差异；跳转修改位置；恢复单个受管理文件版本 |
| 实验与成果 | 检查数据概要、对比实验、预览图表、打开论文草稿和导出包 |
| 控制区 | 查看模型和环境状态、预算、权限范围；暂停、取消、恢复任务 |

面向用户显示计划、行动和验证证据，不要求提供商输出隐藏思维链，也不将隐藏思维链作为审计材料。

### 对话与输出约定

主对话采用连续、紧凑的工作记录，让用户看清当前判断、实际动作和执行结果。简单问题直接回答；需要研究或操作时，再逐步显示相关过程。

| 内容 | NEXIOM 的呈现方式 |
| --- | --- |
| 分析摘要 | 简述问题理解、关键假设、方法选择依据和不确定点；长摘要可折叠。数学推导按需完整呈现，并链接所用数据或依据 |
| 行动说明 | 执行前用一两句说明目的；连续同类操作合并说明，不逐个复述工具参数 |
| 工具记录 | 行内显示工具名称、操作目标和状态，按需展开参数、差异及日志；直接关联真实 ToolCall |
| 过程调整 | 发现数据问题、实验失败或方案变化时，解释原因及下一步；失败状态保持可见 |
| 最终答复 | 先回答用户问题，再交代必要的验证依据、成果入口和未解决项；篇幅随任务复杂度变化 |

“分析摘要”是面向用户的解释，不伪装为模型的完整内部思考。若提供商支持公开的推理摘要，可以按其协议单独呈现；未提供时不补造思考流。科研推导、模型假设和结果解释属于正常成果，应支持公式、表格和图表。

工具流和成果预览共同组成主要反馈：用户能从“运行完成”打开真实实验，从“修改完成”打开差异，从最终结论跳到图表或论文位置。运行状态由核心事件驱动，不能靠模型文本宣告成功。

该呈现方式由消息类型、事件投影和输出约定共同保证，模型接入方式仍独立选择。不会因为参考 Claude Code 的表达就自动决定使用 Claude 模型或 Claude Agent 后端。

运行中发出的新消息在下一个安全边界进入 Agent 上下文；“取消”应立即触发进程终止流程。UI 必须区分“已收到”“将在当前操作后处理”和“任务已停止”。

总体参照范围还包括模型配置、扩展工具和后续自动化；这些按路线逐步加入，不作为首个版本同时交付的条件。自动化应限定为可检查结果的建模任务，例如定时重跑实验，而非没有完成条件的无限运行。

## 3. 首版完整工作流

1. 创建项目，导入赛题 PDF、CSV/XLSX 附件，保留原始文件副本及哈希。
2. 提取题目小问、已知条件、交付要求与数据字段；将无法可靠解析的公式、图片和表格标为待核对。
3. Agent 给出候选建模方案、假设、评价指标、数据处理方式与预计实验范围；用户讨论后批准某个计划版本，同时建立论文结构与符号表。
4. Agent 在批准范围内自主清洗数据、生成程序、执行基线并验证输出。失败时按预算修复并重试。
5. 记录每次实验的数据、代码、参数、随机种子、环境、指标与产物；采用一致数据划分和指标比较候选方案。
6. 对关键结果做约束检查、误差分析、敏感性或稳健性检验；用户接受阶段结论或要求继续实验。
7. 随步骤 3–6 持续将已明确的方法、通过核对的结果、图表、公式解释和引用补入论文草稿；结论链接到实验或外部来源，未解决部分显式保留缺口。
8. 导出论文 PDF、源文件、代码、必要数据及复现说明；用户检查提交清单并自行提交。

第一条工程验证流程可先使用人工可核对的历史赛题片段和小数据集。闭环通过后再扩大到复杂整题，不能用“模型成功回复了”代替数值结果验证。

## 4. 需求优先级与验收

| ID | 需求 | 优先级 | 验收证据 |
| --- | --- | --- | --- |
| PR-01 | 本地项目、会话及持续保存 | 必需 | 关闭并重开应用，历史、待确认计划及产物引用可恢复 |
| PR-02 | 赛题和表格导入、带位置的内容提取 | 必需 | 内容可回到 PDF 页码或表格工作表和单元格；解析失败有明确标记 |
| PR-03 | 可版本化计划、确认后自主执行 | 必需 | 未批准计划不能进入执行；已批准范围内不逐次重复询问 |
| PR-04 | 文件读取、搜索、补丁、命令与 Python 执行 | 必需 | 每次调用有结构化参数、状态、退出码或明确错误 |
| PR-05 | 实验追踪与产物预览 | 必需 | 任意成功实验能找到不可变输入快照、程序、环境和输出 |
| PR-06 | 对照实验与结果核对 | 必需 | 至少两组方案在同一评价协议下可比较；失败实验不参与成功排名 |
| PR-07 | 有依据的草稿与模板导出 | 必需 | 一个完整问题的数值、图表及关键论断均可追溯；PDF 可渲染 |
| PR-08 | 中断、重启恢复、预算上限 | 必需 | 运行进程可取消；崩溃后不自动重放状态未知的写操作 |
| PR-09 | 来源检索与引用管理 | 增强 | 保存来源链接、位置、获取时间与核验状态；未核验内容不能显示为已核验 |
| PR-10 | 模型与扩展工具配置 | 增强 | 切换提供商不破坏项目模型；工具按能力声明接入 |
| PR-11 | DOCX、MATLAB/R、OCR 强化 | 增强/待确认 | 每项在明确运行环境与样例集上独立验收 |
| PR-12 | 子 Agent、后台任务、项目交接改进 | 后续 | 先满足隔离、合并、成本及恢复协议，再引入并行 |

“必需”是首个可用版本的必要范围；“增强”和“后续”表示后续优先级，与路线中的 P0-P5 开发阶段区分。首版允许手动添加和核验引用，在线检索不是完整流程的硬依赖。

## 5. 自主执行和计划变更

批准对象为明确的计划版本，含目标、任务、允许写入目录、工具能力、计算和调用预算、网络范围、验证条件。审批不是一次对话中的模糊“继续”。批准应持续生效，直到范围变更、撤销、预算耗尽或有效期结束。

在范围内，读取文件、生成程序、运行实验、修复可恢复错误、生成图表和整理草稿可自主进行。替换核心建模假设、改变任务目标、访问新增外部数据服务或超出预算时，更新计划并解释影响，由用户确认增量。

“方案批准”“工具能力授权”和“结果接受”分别记录：批准编程不等于接受结论；查看结果也不意味着批准新增权限。

## 6. 质量要求

- 真实性：区分假设、计算结果、文献事实和人工结论；缺失的来源、实验与数值不得由生成文本补齐。
- 可复现性：固定数据与代码快照、环境和随机种子；对非确定性算法记录比较容差和不确定性，不能承诺所有机器逐位相同。
- 长任务可靠性：可查看当前步骤和最后活动时间；持久化在交互确认前完成；应用重启后可解释哪些步骤完成、失败或结果未知。
- 预算：支持 token、模型费用估计、墙钟时间及实验资源限制；未知价格显示未知，费用估计不冒充最终账单。
- 本地性：文件与项目状态默认本地保存；调用远程模型仍可能发送选定上下文，界面应说明本次使用的远端服务。
- 易用性：赛题、数据、运行、图表、论文间可直接跳转；用户能从失败步骤继续工作。
- 竞赛适配：按具体年份和组别配置提交要求及 AI 使用披露字段；未核验的规则标为待核验，不内置跨年份的绝对判断。

## 7. 首版边界

首版不实现多人实时同步、云端训练集群、通用多 Agent 调度平台、完整 Word 编辑器或自动竞赛提交。首版论文能力覆盖草稿与固定模板出口，复杂排版仍可用外部工具精修。

这些边界用于明确验收范围，未来扩展依赖下层契约，不预先引入分布式数据库、向量数据库或微服务部署。
