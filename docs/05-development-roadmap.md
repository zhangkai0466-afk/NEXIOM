# 分阶段开发路线

状态：v0.1。以可运行的验收结果为阶段出口，开发周期待团队人数、接入方案及发布范围确认后估算。

2026-09-19 当前入口：继续设计建模伙伴的功能与交互，详见 [功能设计草案](22-modeling-partner-functional-design.md)。当前 NEXIOM 尚不能承担实际建模工作；先收敛功能和依赖，再分阶段实现、做局部验证，具备完整工作能力后再做整题验证。下面 P0–P5 保留为工程路线参考，不是当前完成度声明，也不要求先用现有版本开展实战。

## 1. 阶段与交付门槛

| 阶段 | 工作与交付物 | 验收门槛 | 前置条件 |
| --- | --- | --- | --- |
| P0 架构收敛 | 评审本套文档；确定平台、模型接入、文档出口；做最小技术验证并记录 ADR | 流式响应、一次受控工具调用、取消、Python 启动、文档样例导出均有证据；技术路线只保留一个首版 Runtime | 用户认可架构方向后再开始验证代码 |
| P1 桌面和可靠性基础 | 项目/会话、Host/Core 协议、SQLite、事件恢复、文件快照、凭证代理、进程控制 | 桌面可建项目；重启恢复记录；中文/空格路径可用；Renderer 无直接执行权限；取消能终止子进程树 | P0 路线已定 |
| P2 最小 Agent 工作流 | 讨论、版本化计划、批准、工具循环、文件补丁、进程执行、预算、重试和中途输入 | 从一个小 CSV 任务讨论到批准，生成并运行代码，返回真实图表；工具失败可解释；已批准范围内连续执行 | P1、真实提供商接入 |
| P3 数学建模工作区 | 赛题解析、数据版本、ProblemSpec/ModelSpec、实验协议、追踪与对照 | 两个方案在同一协议下可比较；输入和代码可复现；失败结果不混入有效结果；论断可追溯 | P2 稳定 |
| P4 论文和首版交付 | 证据链接、论文块、模板导出、引用检查、复现包、安装包 | 一份选定历史赛题样例完成导入到交付；导出 PDF 可读；代码在干净支持环境重跑；来源和数值无断链 | P3、文档出口已定 |
| P5 扩展与增强 | MCP、在线检索、更多模型和计算环境、DOCX、有限子 Agent、后台任务 | 每项扩展有独立评测、权限与恢复契约；没有扩大基础模块职责 | 已有首版用户反馈和基线指标 |

P4 是首个面向用户的完整版本。P2 是内部工程里程碑，不能将“会调用工具的聊天窗口”视为数学建模产品已完成。

需求映射：P1 覆盖 PR-01 和 PR-08 的恢复基础；P2 覆盖 PR-03、PR-04 和 PR-08 的执行控制；P3 覆盖 PR-02、PR-05、PR-06；P4 覆盖 PR-07 并整体验收 PR-01 至 PR-08；P5 逐项覆盖 PR-09 至 PR-12。模型认证、基本引用记录和进程控制属于首版基础，不能因增强项中存在类似名称而推迟。

## 2. P0 应做的决策验证

| 决策 | 最小验证 | 不通过时的调整 |
| --- | --- | --- |
| Runtime / 模型接入 | 确认官方认证与集成方式；收集一次流式输出、工具往返、取消、错误事件及用量 | 选可支持的直接 API；不依赖未证实的订阅或登录复用 |
| 本地计算 | 在目标 Windows 环境执行带空格和中文路径的 Python 项目，取消其子进程，恢复日志 | 先使用明确支持的已安装环境；必要时缩小运行时范围 |
| 沙箱承诺 | 明确受信任本机执行与真正沙箱的差别，验证所选隔离方案能力 | 首版如实提供受信任执行，不发布无法兑现的目录/网络隔离声明 |
| PDF 与论文出口 | 解析一份含中文、公式和表格的赛题；渲染一份含中文、公式和图表的论文样例 | 更换解析/渲染工具；保留人工核对入口；若要求 DOCX 则调整来源模型 |
| 桌面基础 | Host/Core 启动、事件推送、Core 异常退出及恢复 | 优先修复生命周期，暂缓额外面板 |
| 安装范围 | 确认 Python、排版工具、字体和原生数据库依赖的安装或检测策略 | 缩小首版支持矩阵，提供可诊断的依赖检查 |

架构初稿阶段仅形成设计。用户后续提出初步搭建意向后，已开始桌面与本地核心验证，范围见 [基础版说明](06-bootstrap-status.md)；模型和文档出口仍未验证，不将 P0 整体标为完成。

## 3. 按真实场景验收

| 场景 | 通过标准 |
| --- | --- |
| 方案未批准 | 可以阅读和讨论；生成代码执行被阻止；不会借通用 shell 绕过 |
| 批准后连续工作 | 计划内编程、实验、修复、图表生成连续进行，不重复请求相同授权 |
| 实验执行失败 | 保留退出码和日志；不产生成功指标；修复后创建新实验 |
| 用户在执行中纠正目标 | 输入可见且已持久化；下一决策采用新约束；范围变更触发计划修订 |
| 对话过程与输出呈现 | 分析摘要、简短行动反馈、可展开的真实工具记录及最终答复按顺序呈现；历史恢复一致；简单问答不强制展示整套过程 |
| 撤销授权与迟到审批 | 已撤销或旧版本审批不启动新调用；运行中任务按取消策略处理 |
| 执行后、结果落库前崩溃 | 调用显示结果未知；先检查产物/进程，不盲目重复副作用 |
| 用户修改同一个文件 | 哈希检查报告冲突，用户编辑得到保留 |
| 论文数字失效 | 数据或代码变化后相关检查显示过期，可跳回原实验与指标 |
| 网络不可用 | 本地文件、历史与已安装环境仍可使用；模型请求明确失败并可恢复 |
| 项目路径和恢复 | 中文、空格、长路径、移动项目、一致性备份恢复可用 |
| 附件含指令性文字 | 被当作材料；不会改变系统策略、泄露凭证或直接触发授权 |
| 文档与数据异常 | 损坏文件、超大表格、缺失单位、NaN 指标能被定位并解释 |

## 4. 评测与质量目标

首批建立 3 类固定样例：数据分析/预测、优化决策、动态或机理模型。每类选择可合法使用且能人工核对的历史材料，保留输入、预期检查、参考结果或容差以及复现环境。

评测分两层：确定性协议和恢复检查使用假 Runtime/固定工具结果；真实 Agent 端到端评测固定模型版本、预算及样例，多次运行记录差异。不能以一次模型成功证明长期可靠，也不能对自然语言输出做逐字断言。

首版硬门槛：所有已标记成功的实验可定位其输入/代码/环境；所有标记已核验的论文数值都有有效来源；既定取消、冲突和崩溃样例通过；导出包无凭证并能在支持环境重跑。模型任务成功率、平均费用、耗时与峰值资源先建立实测基线，再确定可承诺的阈值。

UI 性能初始目标：提交输入和取消操作在本地 300 ms 内给出已接收反馈；最终终止耗时独立测量并显示。该目标需在明确的参考硬件上验证，不能把模型响应速度纳入本地 UI 保证。

## 5. 建议代码组织

建议目录如下。基础版先创建已承担实际职责的模块，后续模块按验证结果增加：

```text
apps/desktop/          Electron Host、preload、Renderer
packages/contracts/    命令、事件、工具与领域 schema
packages/core/         项目、任务、Agent、策略、上下文、持久化
packages/runtime/      选定的 Runtime 和模型适配
packages/tools/        内置工具与工作进程桥接
packages/research/     数据、模型、实验、证据、论文
workers/python/        计算与文档工具的明确入口
fixtures/              可复现样例和异常用例
docs/                  需求、架构、ADR 与验收记录
```

逻辑包可先保留在一个 workspace 内，依赖关系清楚即可；无需起步就发布每个包。已有 `assets/brand/` 和 `tools/` 继续保留。
